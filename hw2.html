From wallet seed to Ethereum address

A wallet such as MetaMask turns twelve words into an Ethereum address through six standards, each built on a different cryptographic primitive. This page runs the whole pipeline in the browser, explains the job of every step and measures the statistical properties of the hash functions and checksums involved.

    3 Five different jobs

    generation vs derivation

    Key generation creates new secret randomness: the 128 bits of entropy behind the twelve words. It is the only step that needs a random number generator, and all the security of the wallet comes from it.

    Key derivation computes more keys from an existing secret, deterministically: the seed from the words (PBKDF2), the master key from the seed and every child key from its parent (BIP-32). It adds no entropy, so the same phrase always rebuilds the same wallet.

    public-key cryptography

    Two mathematically linked keys: the private key k stays secret, the public key Q = kG can be shared. Anyone can verify a signature with Q, only the owner of k can produce it. The link is one-way because of the ECDLP. Only secp256k1 does this in the pipeline.

    hashing

    A public, keyless function that maps any input to a fixed-size digest that looks random, is hard to invert and makes collisions hard to find. Keccak-256 turns the public key into the address; SHA-256 and SHA-512 appear inside BIP-39 and BIP-32.

    checksums

    Extra information computed from the data so that accidental errors are detected. They protect against mistakes, not attackers. BIP-39 uses the first bits of SHA-256(entropy) as the last bits of the last word; EIP-55 hides a checksum in the capital letters.

    encoding

    A reversible change of representation with no secret and no security: bits to words (BIP-39), bytes to hexadecimal, hex to mixed case (EIP-55). Encoding makes data easier for people or programs to handle.

    4 Historical context

    1. 1977RSA: first practical public-key cryptosystem.
    2. 1985Elliptic-curve cryptography proposed independently by Koblitz and Miller.
    3. 2000secp256k1 published in SEC 2; later chosen by Bitcoin (2009) and Ethereum.
    4. 2001SHA-2 (SHA-256, SHA-512) standardized by NIST.
    5. 2008Keccak submitted to the NIST SHA-3 competition; it wins in 2012.
    6. 2012BIP-32: hierarchical deterministic wallets.
    7. 2013BIP-39: mnemonic code for the seed.
    8. 2014BIP-44: standard multi-account derivation paths.
    9. 2015Ethereum launches in July with Keccak-256; in August NIST publishes SHA-3 (FIPS 202) with a different padding.
    10. 2016EIP-55: mixed-case checksum addresses.

    The primitives are old and well studied (RSA 1977, ECC 1985, SHA-2 2001), while the wallet standards on top of them are recent and come from the Bitcoin community (2012–2014). Ethereum adopted them and added only what it needed: Keccak-256 addresses and the EIP-55 checksum. Because Ethereum fixed its hash function while SHA-3 was still being finalized, it kept the original Keccak padding.

    6 Why several primitives instead of one

    Each step solves a different problem, and the properties needed by one step would be wrong for another:

    • BIP-39 / BIP-32 / BIP-44 → key management. A person must back up one secret and restore every key from it. This needs a human-friendly encoding, a slow key-stretching function (PBKDF2 makes each guess of a phrase 2048 times more expensive) and a deterministic tree of keys. A hash alone gives none of this.
    • secp256k1 → ownership and signatures. Only an algebraic structure gives a public key that can verify signatures made with the private key. A hash has no such structure: knowing H(k) does not let anyone check a signature.
    • Keccak-256 → a short, uniform identifier. The public key is 64 bytes and has the structure seen in HMWK 1. Hashing removes that structure and shortens it to 20 bytes, while finding another key with the same address is infeasible.
    • EIP-55 → error detection. A typo in an address sends money to the wrong place forever. A checksum catches it, and EIP-55 does this without breaking existing lowercase addresses.

    Separating the jobs also limits damage: a weakness in one primitive does not automatically break the others, and each part can be replaced or studied on its own. It is the same principle as layering in network protocols.

    7 Statistical properties

    Each experiment checks a property that one of the primitives is supposed to have. The tests run in the browser when the page opens; press the button to repeat them with new random data.

    7.1 Keccak-256: avalanche effect

    Random 32-byte messages are hashed, one random bit is flipped, and the two digests are compared. For an ideal hash each of the 256 output bits changes with probability ½, so the number of changed bits follows a Binomial(256, ½): mean 128, standard deviation 8.

    7.2 Uniformity of addresses

    Addresses are derived from the phrase in section 1 along m/44'/60'/0'/0/i. If Keccak-256 output is uniform, each of the 16 hexadecimal digits appears with probability 1/16 and each of the 160 address bits is 1 half of the time.

    7.3 Independence of derived keys

    BIP-32 child keys for consecutive indexes i and i + 1 are compared bit by bit. If HMAC-SHA512 behaves like a random function, about 128 of the 256 bits differ, even though the indexes differ by one.
